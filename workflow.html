A collection of engineering skills with a clear path from discovery to a verified local result. Task approval and implementation-model approval are separate decisions. Delivery stays local until you authorize it.

01

Compose, don't duplicate

Conductor skills are thin routers. Each behavior lives in exactly one skill and is referenced, never copied.

02

Ask useful questions

The interview investigates first and asks exactly five independent questions when five exist, otherwise fewer, never more.

03

Keep approvals distinct

The task queue defines the work. A later model plan defines the implementation and review route.

04

Vertical slices

The unit of work cuts through every layer, is demoable alone, and ships with a machine-checkable acceptance contract.

The handoff contracts

decide once, carry forward

Each stage uses the evidence from the previous one. The PRD names the behavior and constraints. The task queue makes acceptance and engineering checks explicit. The implementation plan adds the models and effort before work starts.

to-prd

Synthesize the PRD

No new interview. It turns the decision record into a draft PRD for user review.

Security Decisions record the relevant threat-model decisions
Success conditions name the observable behavior that the task must preserve
→
to-tasks

Cut vertical slices

Tasks begin in a draft. User approval publishes task slices that carry the PRD's requirements forward.

acceptance gives observable behaviors and evidence
engineering checks select the gates, lenses, and practice skills
→
implement-tasks

Approve the model plan, then build

The task approval does not select the models. The implementation plan names the requested implementation and review models, execution paths, effort, model-verification policy, and any unavailable seat.

model_verification requires a verified receipt or permits an approved unverified route
a configured model name is not proof that it served the run
native subagents or supported task threads keep each role through its later turns
a local verified result is the default delivery point

The design-gate router

judgment → lookup

"Which design lens applies?" is itself a mid-flight question waiting to happen. design-gate turns it into a table: it reads the surfaces a change touches, runs at most three lenses as parallel read-only reviewers, and returns proceed, revise, or decision_required.

Implementation and review

route by task shape

The shared routing rules select the right engineering practice. The model plan names the requested implementation and review routes and their receipt requirements before any worker starts.

implement-and-review
scope · one task

Completes one scoped task with the selected gates, lenses, practice skills, tests, and review. It produces evidence for the task acceptance contract.

applies coding-design-plan · design-gate · tdd · full-review when the task needs them
implement-tasks
scope · approved task queue

First shows the task-shaped route and effort plan. After approval, it uses an exact native model in a persistent role context, or an approved runner for a foreign route, then verifies the local result. Integration requires separate authorization.

calls implement-and-review for each approved task
models-consensus
scope · explicit request for more opinions

A user-invoked, deliberation-only council. No workflow or model invokes it. It previews the seats and effort, waits for roster approval, then returns a decision record. Routine reviews do not invoke it.
