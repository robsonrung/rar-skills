Workflow Call Map

Four stages, one task engine, and a defined handoff at each boundary. Engineering skills run when they can change a decision, implementation, or review.

interview-me1 · settle requirements
to-prd2 · approve the PRD
to-tasks3 · approve the task queue
implement-tasks4 · approve models, then execute

Call map

PRD approval, task approval, and model approval cover different decisions. The implementation stage asks for a new decision only when the approved scope, route, or authority no longer covers the work. Independent work can continue.

PRDNo new engineering passSynthesize settled choices. Return a material gap to the interview.

Inside a worker

Start with one task and one implementation track. Add a track only when it can proceed independently against an agreed contract. Model approval precedes execution; --auto does not bypass it.

Apply the contractReuse decisions and lens findings.
ImplementUse the approved model and effort.
Review and fixUse the approved independent reviewer.
Return evidenceThe parent verifies integration.

At most three review/fix cycles and one evidence recovery per task. Record an attempt before dispatch. A missing model blocks its route unless the exact fallback was already approved.

Step 1

interview-me

Settle the choices that shape the PRD

Use relevant repository facts, vocabulary, and prior decisions. Ask exactly five independent frontier questions when five exist and the interface permits; otherwise fewer, never more. Security questions share that limit. A material choice requires a user answer or an explicit scope boundary.

Write .ai-workflow/work/<feature-slug>/decision-record.md as draft, then ready-for-prd when the frontier is empty. Record glossary entries and qualifying ADRs when decisions settle.

Use one relevant broad lens at a time. Do not run the design gate, test lens, implementation practices, or a council inside the interview.

Step 2

to-prd

Write and approve the specification

Receive the ready-for-prd decision record. Write .ai-workflow/work/<feature-slug>/prd.md with status draft. Preserve goals, journeys, observable outcomes, settled design and security choices, rollout constraints, and scope limits.

Present the draft for approval. Set status to approved only after the user accepts it. The approved PRD is the input to to-tasks.

Do not open a second interview, plan files or test mechanics, select models, or call engineering gates. Return a material conflict or missing decision to interview-me.

Step 3

to-tasks

Approve executable slices

Receive an approved PRD. Write tasks-draft.md with stable task IDs, dependencies, observable acceptance, verified command definitions, gate results, security classification, rollback, review focus, and parallelization limits.

CallWhen and result
design-gateOnce per slice. Run at most three relevant lenses as read-only reviewers. A local change may need no lens. Resolve blocking findings; recheck only the lens that raised a finding.
security-gateClassify each slice as deep or standard and record the matched trigger.
test-lensOnly for a real choice about test value, seams, mocks, concurrency, or brittle tests.

After task approval, set the draft queue to approved and publish tasks/T<N>-<slug>.md with status ready-for-agent. Published slices have verdict: proceed and decision_required: none. Keep stable IDs and preserve tasks already in progress.

Task approval defines the queue. It does not approve implementation model routes or external delivery actions.

Step 4

implement-tasks

Approve models and coordinate execution

Validate the queue and prepare model-plan.md. Resolve the strongest suitable models from the maintained roster, then select the lowest sufficient supported effort. Use the same approval for a complete single task.

Preview fieldWhat the user sees
AssignmentsTask IDs, implementation role, independent review role, and integration scope.
RoutesExact models, runners, efforts, and a reason for each selection.
LimitsCoordinator, concurrency cap, review/fix ceiling, planned specialists, and any proposed fallback.
Model evidenceWhether a serving-model receipt is required or the user accepts an unverified serving model.

Wait for explicit approval or changes. Save routing-plan.json with the response reference, timestamp, task-content hashes, and route digest. Task approval, silence, or --auto cannot approve model use. A matching prior approval can be reused.

After approval, dispatch implement-and-review for ready tasks. Use one fresh context per task, with paths and a short brief. Record progress in run-state.json. Without isolation, use one sequential writer. Commit-based integration requires explicit commit authority.

Verify the combined state before releasing dependent tasks. Run the approved feature review once for cross-task seams; a single task with complete scoped review does not need a duplicate panel. Reuse matching evidence and rerun affected or explicitly required checks.

Deliver the verified local diff by default. Reuse explicit authority for commits, push, and PR work. Do not create user-owned tasks, goals, or sidebar changes as routine execution. A material new decision pauses the affected task; independent work continues.

Task engine

implement-and-review

Build and review one approved task

Use the exact routes in the approved plan. The launcher checks the task hashes and route digest before side effects. Derived briefs keep the task contract, write scope, acceptance, relevant lens findings, and evidence paths.

The independent reviewer uses the approved model in a fresh read-only context. The approved implementer applies valid findings within the cycle limit. Do not weaken acceptance to obtain a pass. Report complete, failed, ceiling_hit, or awaiting_human with acceptance evidence, model receipts, findings, and changed paths.

The parent marks a task done after integration acceptance. A completed worker report alone does not complete the queue.

Optional council

models-consensus runs only when the user explicitly asks for extra model opinions. No workflow calls it as an automatic escalation.

Before any call, show the exact seats, model labels, roles, effort, receipt requirements, transport, and call budget. Wait for approval or changes. Keep the council read-only and report agreement, dissent, evidence gaps, and separate answer and diversity confidence.

A council result can inform a later decision. It does not approve implementation or substitute for the implementation model plan.

Routing rules

  1. Resolve facts before asking.Use relevant repository evidence. Ask only for decisions the evidence cannot settle.
  2. Reuse settled decisions.Carry decisions and lens findings through the handoffs. Reopen only when new evidence changes them.
  3. Load the selected method.Use short entry files to select supporting documents at the point of need.
  4. Keep real order constraints.Approval precedes dispatch, a failing behavior test precedes its fix, and integration acceptance precedes dependent tasks.
  5. Reuse valid checks.Evidence must match the relevant code, dependencies, environment, and contract. Required fresh checks still run.
  6. Keep exact model approval.Unavailable routes block their own work. A substitution needs prior approval for that exact fallback or a new decision.
  7. Record attempts before dispatch.Persist review/fix and evidence-recovery counts. At the ceiling, stop the affected task.
  8. Record only qualifying ADRs.All three must hold: hard to reverse, surprising without context, and a real tradeoff.
