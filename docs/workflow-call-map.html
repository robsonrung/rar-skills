Workflow Call Map

Use four stages for a feature or enter the existing task engine directly for one specified change. Both paths retain exact worker approval and independent review. Methods and commands stay in the current role unless a real gap needs another worker.

Call map

PRD, task, and model approval cover distinct decisions. Task-only approval is the default. When execution is requested, one response can explicitly approve the queue and exact worker plan, with separate input bindings. A changed scope, route, or authority needs the applicable decision; independent work can continue.

Inside a worker

Start with one task and one implementation track. Add a track only when it can proceed independently against an agreed contract. Apply routine practices and lenses in that role. Independent specialists need a material risk or unresolved question and an approved route. Exact worker approval precedes dispatch; --auto does not bypass it.

Apply the contractReuse decisions and lens findings.
ImplementUse the approved model and effort.
Review and fixUse the approved independent reviewer.
Return evidenceThe parent verifies integration.

Honor the approved review/fix and evidence recovery allowances, with defaults of three cycles and one recovery per task. Reserve each native or runner call before dispatch. Resume does not reset limits. A missing route needs its exact approved fallback or a new decision.

Step 1

interview-me

Settle the choices that shape the PRD

Use relevant repository facts, vocabulary, and prior decisions. Ask exactly five independent frontier questions when five exist and the interface permits; otherwise fewer, never more. Security questions share that limit. A material choice requires a user answer or an explicit scope boundary.

Write .ai-workflow/work/<feature-slug>/decision-record.md as draft, then ready-for-prd when the frontier is empty. Record glossary entries and qualifying ADRs when decisions settle.

Use one relevant broad lens at a time. Do not run the design gate, test lens, implementation practices, or a council inside the interview.

Step 2

to-prd

Write and approve the specification

Receive the ready-for-prd decision record. Write .ai-workflow/work/<feature-slug>/prd.md with status draft. Preserve goals, journeys, observable outcomes, settled design and security choices, rollout constraints, and scope limits.

Present the draft for approval. Set status to approved only after the user accepts it. The approved PRD is the input to to-tasks.

Synthesize the settled record. Return a material conflict or missing decision to interview-me. This coordinator-only branch needs no worker preview.

Step 3

to-tasks

Approve executable slices

Receive an approved PRD. Write each complete contract in tasks/T<N>-<slug>.md as draft. Include stable IDs, acceptance, verified command definitions, gates, security, rollback, review focus, and ownership. Use tasks-draft.md as a compact index and queue.json for machine scheduling inputs.

MethodWhen and result
design-gateOnce per slice. Apply at most three relevant inline read-only lenses. A local change may need none. Resolve blocking findings; recheck only the lens that raised a finding. A material gap can require an approved specialist.
security-gateClassify each slice as deep or standard and record the matched trigger.
test-lensOnly for a real choice about test value, seams, mocks, concurrency, or brittle tests.

Keep an immutable preview of the PRD, index, queue, and draft and prospective ready task identities. After approval, change only the exact status line and verify the ready content hashes. Keep stable IDs and existing legacy queue records.

Task-only approval is the default. If execution is requested, one response can explicitly approve both the queue and exact worker plan. Preserve separate decision bindings and the actual response. Drafts cannot run; task-only approval cannot satisfy the model gate.

Step 4

implement-tasks

Coordinate approved execution

Validate canonical queue inputs and reuse matching combined approval. Otherwise resolve only needed worker routes through the central configuration with --profile default, validated local preferences, and explicit overrides. The configuration selects the default. Approved snapshots preserve exact selections.

The read-only task_queue.py controller projects ready, blocked, and required_integration work from bound inputs, manifests, and the existing ledger. It starts no worker and reserves nothing. The conductor reserves selected calls before dispatching implement-and-review. Retain ownership through pending work and integration. Without isolation, use one sequential writer. Shared surfaces require serialization or an approved merge plan.

Verify the combined state before releasing dependent tasks. Reuse current launcher review evidence when its exact route and combined source still match. A single task with complete scoped review needs no duplicate panel. An extra integration reviewer call needs its separately approved scope and reserved allowance. Rerun affected or explicitly required checks.

Deliver the verified local diff by default. Commit-based integration, push, and PR work retain explicit authority. Routine execution does not create user-owned chats or sidebar changes. A new material decision blocks only the affected work.

Verification and recovery

The shared review_evidence.py select-checks command selects affected commands from declared inputs and changed paths. Run affected and required fresh checks. Keep matching captures. A candidate transfer needs explicit current runtime, dependency, external state, and base interaction evidence. Unknown dependencies use whole-source scope.

validate-e2e, browser-smoke, and review use the same captured command and observation shape. Export the current validation evidence-packet, give it to the independent reviewer, preserve the actual response, then run the shared verifier. pre-pr-review reuses accepted evidence and closes only missing work. A generic status map or prose pass cannot supply command evidence or reviewer judgment.

Claude preflight caches stable capabilities with a current CLI, routing and preflight code, configuration, policy, launch-context, model, and effort fingerprint and a 24-hour limit. Each launch still checks authentication visibility and installation drift. Serving receipts, entitlement, quota, tool permissions, and request privacy remain current-run facts.

Reserve calls and recovery attempts before execution. Reconcile pending native or runner work before retrying. Retain original logs, immutable source bindings, independent role contexts, and consumed budgets across resume. A runtime gate failure remains a failure even when business behavior passes.

Optional discovery and council

models-consensus runs only when the user explicitly asks for extra model opinions. No workflow calls it as an automatic escalation.

Before any council call, show exact seats, roles, effort, receipts, transport, privacy controls, and the complete base, conditional, and recovery budgets. Obtain separate council approval. Modes are poll, debate, and personas. Poll defaults to standard.

Explicit lean is for low-risk questions through per_call transport; cmux rejects it. Both judge routes are approved before opening calls. Validated organizer evidence requires both judges for material gaps, contradictions, low confidence, or high risk. Otherwise an immutable organizer evidence record establishes conditional-not-needed. Security, money, migrations, public contracts, data loss, deep review, and high risk require standard.

brainstorm batches up to five independent decisions after its territory gate. to-prototype tests one question with the smallest useful experiment, such as one visual fixture or two alternatives when comparison matters. Add a host page only when real application context changes the observation. Prototype code remains disposable.

A council result can inform a later decision. It does not approve implementation or substitute for the implementation model plan.

Routing rules

  1. Resolve facts before asking.Use relevant repository evidence. Ask only for decisions the evidence cannot settle.
  2. Reuse settled decisions.Carry decisions and lens findings through the handoffs. Reopen only when new evidence changes them.
  3. Load the selected method.Use short entry files to select supporting documents at the point of need.
  4. Keep real order constraints.Approval precedes dispatch, a failing behavior test precedes its fix, and integration acceptance precedes dependent tasks.
  5. Reuse valid checks.Evidence must match the relevant code, dependencies, environment, and contract. Required fresh checks still run.
  6. Keep exact model approval.Unavailable routes block their own work. A substitution needs prior approval for that exact fallback or a new decision.
  7. Record attempts before dispatch.Persist review/fix and evidence-recovery counts. At the ceiling, stop the affected task.
  8. Record only qualifying ADRs.All three must hold: hard to reverse, surprising without context, and a real tradeoff.
