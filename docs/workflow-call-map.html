Workflow Call Map

Four skills you type, one build engine they hand to, and every skill those five call along the way: when the call happens, what condition triggers it, and the principle that decides it.

interview-me1 · grill until spec-ready
to-prd2 · write the autonomy contract
to-tasks3 · slices + contracts · the last gate
implement-tasks → implement-and-review4 · conduct · build one task per worker

Call map

The spine runs left to right. Everything to the left of the gate may still ask the user; everything to the right must not. Beneath each step are the skills it calls. A solid edge always runs, a dashed edge runs only under the condition written on it, and a dotted edge means the step reads that skill's table or rules and records only the result.

Inside a worker

Each task worker runs the full implement-and-review engine on exactly one task. Phases run left to right; the two crimson loops are the only places the engine goes backwards, and both are capped at three by a counter on disk.

Step 1

interview-me

Grill the idea until nothing is silently assumed

Stress-tests a feature idea against the code, the glossary in CONCEPTS.md, and past decisions in docs/adr/, in frontier rounds: every question that can be asked now without guessing at an unheard answer goes in one round, each with a recommended answer. Decisions are recorded the moment they settle. It ends when the frontier is empty and the spec-ready test passes: every question the autonomous phases would otherwise ask is answered, an explicit assumption with a default, or descoped.

Reads

  • CONCEPTS.md
  • docs/adr/
  • the code the feature touches

Writes

  • glossary entries in CONCEPTS.md
  • ADRs in docs/adr/ (only when a decision passes all three tests)
  • a decision record in the conversation

What it calls, and why

CallsWhenPrinciple behind the call
security-gateThe feature exposes a security surface. Runs the threat-model-lite rows that skill owns.Compose, don't duplicate. The rows live in one skill and are referenced; only the answers are recorded, so to-prd can lift them.
test-lensFor every major requirement.Observable behavior at the highest seam. The seams named here become the PRD's Testing Decisions and, later, slice acceptance behaviors.
to-prototypeBoth tests hold: only running code can settle the question, and the answer changes what gets built. The detour pauses only the branch that hangs off the question.Facts are your job, decisions are the user's. Never guess a prototype question; never prototype what reading could answer. A prototype whose answer would not change the spec is a curiosity recorded as an assumption.
capture-learningOnly when CONCEPTS.md does not exist yet and the first entry is ready to write.The vocabulary rules have one owner. Read them there once, at creation time.
extraction subagentA frontier question needs a fact not yet found in the repo.The user's time is the bottleneck. A question exploration could answer is never asked; only the questions downstream of that fact wait.

Principles it works by

  • Frontier rounds. Two questions that could reshape each other are never in the same round; a question that depends on another still open waits for the next round.
  • Recommendation, not survey. Each question carries a recommended answer with a one-line reason.
  • Already decided. An ADR is an input, not a question; it re-opens only with new evidence.
  • All three or no ADR. Hard to reverse, surprising without context, a real trade-off. Most simple features produce none.
  • Record on settle. Docs are written when a node settles, not at the end, while the Consequences are fresh.

Not brainstorm (decides whether to build, before this), not coding-design-plan (file-level planning, after the spec), not diagnose (root-causes a bug). Hands off with “run to-prd”.

Step 2

to-prd

Write the autonomy contract

Synthesizes the PRD from the conversation without a second interview and writes it to .ai-workflow/work/<feature-slug>/prd.md. It is the last artifact written while the human is in the room, so two sections are load-bearing downstream: Security Decisions, which pre-mark security-sensitive surfaces, and Testing Decisions, which name the seams and the observable behavior at each.

Reads

  • the step-1 conversation and decision record
  • CONCEPTS.md and docs/adr/ for the area touched
  • the code, if not already explored

Writes

  • .ai-workflow/work/<slug>/prd.md with Status: ready-for-agent

What it calls, and why

CallsWhenPrinciple behind the call
test-lensAlways, in step 2: sketch the seams and check them with the user.Highest seam, fewest seams. Prefer existing seams; the ideal is one. Each named behavior becomes a slice's acceptance behavior in to-tasks.
security-gateOnly for rows the feature exposes that the conversation left unanswered. Rows an interview-me run already settled are distilled, not re-asked.The one permitted break of the no-interview rule. A security answer can only be collected while the human is present; a missing one becomes an unanswerable gap in an autonomous phase.
multi-model panelOpt-in: the user asks for a multi-model PRD, or the domain, interface, and backend contracts are consequential enough to earn independent seats.The panel replaces drafting, never the contract. The seam sketch, Security Decisions, no-file-paths rule, and output path all still hold.

Principles it works by

  • No second interview. Work from what is already known; synthesize, don't ask.
  • No file paths or code in the PRD. They go stale. The one exception is a prototype snippet that encodes a decision more precisely than prose.
  • Ubiquitous language. The PRD speaks the glossary's vocabulary and respects existing ADRs.

The PRD is the input to to-tasks, which sets each slice's security flag and acceptance behaviors directly from these two sections.

Step 3

to-tasks

Cut slices that carry their own contract — the last human gate

Breaks the PRD into tracer-bullet vertical slices, each cutting through every layer and demoable alone. Every slice carries a Slice Contract: exact acceptance commands verified to exist in the repo, observable behaviors, design-lens flags, a security: deep | standard flag, HITL or AFK class, a rollback note, an expected review focus, and a parallelization statement. The user approves the breakdown once. After this, nothing asks the user anything.

Reads

  • the PRD (or a plan file or URL)
  • CONCEPTS.md, docs/adr/
  • the repo's real test, lint, build, typecheck commands

Writes

  • one file per slice: .ai-workflow/work/<slug>/tasks/T<N>-<slug>.md, blockers first
  • never an issue tracker, never a combined file

What it calls, and why

CallsWhenPrinciple behind the call
design-gateFor every slice, by the surfaces it touches.Read the routing table, record only the flags. No lens runs here. Choosing among ten lenses is itself a mid-flight question; the flag turns it into a lookup the builder honors as-is.
security-gateFor every slice. When the PRD has a Security Decisions section, the flag is lifted from there rather than re-derived.Lift, don't re-derive. Re-deriving what an approved artifact already states invites drift.
test-lensWhen the source is a to-prd PRD: behaviors are lifted from its Testing Decisions and named at the highest seam.Machine-checkable done. “Tests pass” alone is never acceptance for a feature-bearing slice; the behavior is named.
multi-model panelOpt-in: the user asks for a multi-model task plan, or the architecture and test strategy are consequential enough.The panel replaces steps 3–4 (drafting), never step 5 (the approval quiz).

Principles it works by

  • The contract is the boundary. A slice marked ready-for-agent carries everything needed to finish it unattended; a slice that needs a decision the contract does not answer is never marked AFK.
  • Stable IDs. T-IDs are never renumbered; splits take the next unused number; gaps are fine.
  • HITL first, prefactoring first. Human touchpoints cluster at the start; a behavior-preserving prefactor lands before the slice that needs the easier shape.
  • Wide refactors are expand → migrate → contract, never forced into a vertical slice.
  • Contract integrity. Never delete, skip, weaken, or mock-away tests to make the contract pass. A wrong contract is reported, not edited around.

Does not edit the parent PRD and never rewrites a slice an executor has already moved past ready-for-agent.

Step 4

implement-tasks

The thin conductor

Turns the approved queue into an integrated, reviewed, delivered change without asking anything further. It owns scheduling, integration, the feature-wide review, and delivery, and nothing else: per-task building is implement-and-review's job. Every task runs in a newly created worker (a subagent, or a new thread on the Codex / ChatGPT app) that is first given a checkable /goal, then its brief, and is archived once its envelope is recorded. The orchestrator thread is named ORCHESTRATOR · implement-tasks · <feature> and pinned.

Reads

  • the task queue (or a plan, or a models-consensus report via --from-consensus)
  • git remote, once — no remote means local-only for the whole run
  • the seat probe: Codex, Opus, Kimi

Writes

  • impl/feature-<id> integration branch
  • run-state.json with gates, side_effects, steps, threads
  • docs/residual-review-findings/<sha>.md
  • the PR, or local commits in local-only mode

What it calls, and why

CallsWhenPrinciple behind the call
to-tasksThe input is a bare plan or spec rather than a published queue.The task queue is the input. A genuinely single task skips the DAG and goes straight to implement-and-review.
implement-and-reviewEvery task, as soon as its blockers are integrated, up to the concurrency cap (default 3). Always in a fresh worker with a /goal whose clauses are checkable from disk and shell.One task, one worker, one goal. Hand off the path, not the payload: what crosses back is a report on disk plus a ≤15-line envelope. The orchestrator never builds inline and never reuses a worker.
full-reviewOnce, after every task integrates, on the diff against the feature base, focused on cross-task seams. security_focus=true if any task was security: deep.Each gate runs once. Per-task reviews already ran inside each worker; the feature pass pays only for what they could not see.
models-consensusA task build or the seam review hits a contested or irreversible decision. Poll mode, --auto. Also accepted as an intake source.Escalation ladder replaces mid-flight questions. Deliberation only, never code. Unresolved → most reversible default, recorded in the decision log. Hard-stop for a human only on destructive or irreversible operations.
open-prPhase 3, unless git remote returned nothing at preflight.Local-only is a terminal state, not an error. Zero push or PR retries; the commits, the residual record, and the handoff note are the deliverable.
capture-learningThe run solved a non-obvious problem. Headless mode.Knowledge compounds only when it is written down where the next run can find it.
session-handoffThe run outgrew its session.Progress lives in the ledger, not the transcript. A run survives compaction and restart from run-state, not memory.
resolve-pr-feedbackLater, when review comments arrive on the PR.The human merges; the loop closes on their comments.

Principles it works by

  • Nothing asks the user after the approval. The to-tasks approval is recorded in gates; a resumed run that finds it never re-asks.
  • Evidence or no delivery. A task reported built without verification evidence gets exactly one recovery re-invocation, counted on disk; then it is hard-blocked.
  • Integrate in dependency order. Each task builds on the current integration head, not the stale base; a task must pass its acceptance before dependents start.
  • Side effects are keyed before they happen (merge:, archive:, commit:, pr:, ticket:), so a resumed run merges once and files each ticket once.
  • Residual findings become durable as tickets plus a committed record, never a PR-body ledger.
  • Never fabricate a seat; degrade and say so.

Does not reimplement implement-and-review: the FE/BE split, TDD, cross-review, self-simplify, and the per-task full-review all live there.

Engine

implement-and-review

Build one task with two seats that review each other

Implements one scoped task through two model tracks, frontend and backend, that build test-first in isolated worktrees and review each other's work, then converge on one integrated, reviewed, green change. The orchestrator classifies the task shape and dispatches seats; it never writes a track itself. It runs standalone on a bare prompt, and when the task is a to-tasks slice it lifts the Slice Contract whole: type, acceptance, gates, expected review focus, and rollback note each have a consumer.

Reads

  • the task (prompt, tracker brief, or Slice Contract)
  • the seat probe: Codex, Opus, Kimi, Grok
  • how the project runs a single test — TDD needs a fast inner loop

Writes

  • impl/<T>-backend-<id> and impl/<T>-frontend-<id> worktrees, then an integration branch
  • launch-manifest.json extended with run-state keys
  • report.md and the envelope; the slice's Status line

What it calls, and why

CallsWhenPrinciple behind the call

design-gatePhase 0. With a Slice Contract, the flags set by to-tasks are used as-is, capped at three lenses.Lift the approved flags. The lenses run once, here, as parallel read-only reviewers returning one proceed / revise verdict.
macro-architecture · software-design-philosophy · design-patterns · distributed-systems-patternsOnly when a slice's gates flag them.Planning lenses are expensive; their conclusions enter the briefs as constraints.

An implementer never reviews its own track. The same implementer fixes its own findings; the reviewer re-checks.

full-reviewPhase 4, on the integrated diff against the base, read-only. Re-run (or quick_mode) after any CRITICAL or HIGH fix.The gate runs on the code that ships. Findings are applied by the responsible implementer, with a test per behavioral fix.

Principles it works by

  • Bounded fix loops, counted on disk. At most three review→fix cycles per track and three integration fixes; the counter is incremented before the attempt, so the model never decides the retry.
  • Definition of done is green, and green is earned. Never delete, skip, weaken, or mock-away tests to reach it.
  • Ambiguity in a Slice Contract is a contract defect. A decision the contract does not answer is escalated with the gap named, even under --auto; assumption-and-proceed is for bare prompts only.
  • HITL slices never run under --auto. They park at awaiting_human until the decision is in gates.
  • Evidence contract. Each track captures the red baseline before touching production code and reports it; a track reporting a behavior change without it gets one recovery pass.

Scope is one task. A whole feature, plan, or task list belongs to implement-tasks, which calls this skill per task.

Principles

Nine questions behind every call

The same few tests decide every conditional edge above.

  1. Is the human still in the room?Steps 1–3 may ask; step 4 may not. That is why to-prd asks unanswered security rows, and why implement-tasks escalates to models-consensus instead.
  2. Could reading answer it?If the code, the glossary, or an ADR settles a question, it is read, not asked, and never prototyped. Only a question that reading cannot settle earns a to-prototype detour, and only when the answer changes what gets built.
  3. Was this already approved?A Slice Contract field, a gate in run-state, an ADR: these are inputs. They are lifted as-is, never re-derived, and re-opened only with new evidence. Re-deriving invites drift between what was approved and what gets built.
  4. Does the knowledge have one owner?security-gate's rows, design-gate's routing table, test-lens's seam rule, capture-learning's vocabulary rules: each is read where it lives and only the resulting answer or flag is recorded. Nothing is copied into another skill.
  5. Has the code changed since the last gate?design-gate runs once in Phase 0; coding-review-simplify runs once, before full-review; full-review gates the final code and re-runs only on what changed. No orchestrator re-reviews unchanged code, and no mutating pass follows the final review unreviewed.
  6. Can the seat load a skill?The orchestrator invokes skills. Runner and subagent seats cannot, so methodology travels into their briefs as text, and the reviewer is always a different seat from the implementer.
  7. Is the retry counted somewhere the model cannot forget?Every bounded loop increments a counter on disk before the attempt: fix cycles, integration fixes, evidence recovery. At the ceiling the route is escalation, not another attempt.
  8. Is the operation reversible?Merges, commits, tickets, PRs, and thread archives are keyed before they happen so a resumed run does them once. Only destructive or irreversible operations hard-stop for a human; everything else takes the most reversible default and records the assumption.
  9. Is the seat actually available?Codex, Opus, Kimi, Grok are probed once. A missing seat is degraded honestly with the substitution reported and confidence lowered a band; a seat is never fabricated or silently swapped.
