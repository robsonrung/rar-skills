The catalogue, by family

One line per skill, in the words the skill would use about itself. The small mono line under each card lists the skills it names explicitly, most-cited first. entry marks a skill only you can invoke (disable-model-invocation): no other skill can call it by name mid-run.

II

How they connect

Two kinds of link. A solid edge is an instruction inside a skill to invoke another skill: the pipeline runs on these without you. A dashed edge is a hand-off the docs recommend but nothing enforces: the next step only happens because you type it. Hover any skill to isolate its edges.

The spine you drive

brainstorm → interview-me → to-prd → to-tasks → ship

Each skill ends by naming the next ("run to-prd"), but none invokes it. Outside ship, the chain only exists if you keep typing. ship is the one place the whole spine is wired.

The test-first triangle

safe-incremental-coding ⇄ tdd ⇄ diagnose · test-lens · clean-code

Tightly cross-referenced by "distinct from" clauses. tdd sends untested code to the characterization net and returns; a failure it cannot read at a glance goes to diagnose; test-lens judges what tdd wrote. Only implement-and-review wires them for you.

After the council

models-consensus → decide-about-disagreements · consensus-summary-html · implement-feature --from-consensus

Three consumers of one report. Two of them are entry points, so the council can never hand off to them itself: you read the result, then decide whether to resolve, render, or build.

Memory and continuity

summarize → session-handoff · capture-learning → CONCEPTS.md ← interview-me · knowledge-graph

session-handoff explicitly borrows summarize's body. capture-learning and interview-me both write the glossary. knowledge-graph could feed on the same docs but nothing points it there.

Two ways to review a PR

full-review vs review-gate → verify-changes · browser-smoke

full-review is the human-facing deep review the pipeline calls. review-gate is a machine-verdict merge gate that owns the only call to verify-changes. They share seats and personas but not code.

Explaining a codebase

explain-architecture → architecture-lens · html-explainer · agents-md-craft → skill-expert

Same input (a subsystem), two output shapes (prose vs drill-down HTML), no link between them. agents-md-craft and skill-expert maintain the collection itself.

The frontend cluster

frontend-design · ui-ux-pro-max · react-performance ≈ advanced-react

Reached from implement-and-review's frontend track and design-gate's UI row. advanced-react and react-performance are drawn from the same book and trigger on the same phrases.

Fleets and terminals

dynamic-harness · peer-sessions · cmux-cli · worktree

Orchestration below the skill layer. models-consensus uses peer-sessions for its cmux transport; ship escalates to dynamic-harness manager mode when a run outgrows one session.

III

Where it could get lighter

Twelve findings from reading the skill texts against each other. Each names the evidence in the files, then a concrete move. Tags: cost spends tokens or model seats twice, contract a rule that contradicts another rule, shape two skills where one would do.

01

One slice pays for full-review twice, sometimes three timescost

implement-and-review Phase 3 runs coding-review-simplify and Phase 4 runs full-review on the integrated diff. ship phase 5 then runs the identical chain again on the same code: acceptance → coding-review-simplify → full-review. With implement-feature in the loop, a third feature-wide full-review follows.

full-review is the most expensive skill in the collection (multi-model triangulation, execution-based verification, 28 files). Only implement-feature acknowledges the repeat ("targets the seams so you don't pay to re-review every task in full"); ship does not.

Move

Give implement-and-review a --gate defer input that ship's phase-4 brief sets. The build then stops at green + self-simplify, and phase 5 is the single gate. Standalone invocations keep the built-in gate.

Alternatively keep both but make phase 5 skip full-review when the run state records an APPROVE on an unchanged diff range.

saves one multi-model review per slice
02

The design lenses run before the build, then again inside itcost

Phase 3 dispatches coding-design-plan then design-gate, which runs up to three lenses as parallel reviewers and writes 03-design-gate.report.md. Phase 4's implement-and-review then lists coding-design-plan again under "both tracks" and says of the planning lenses: "the orchestrator runs them in Phase 0 and their conclusions go into the briefs".

The station worker reads the phase-3 report, but nothing in implement-and-review says "if a design-gate report exists, lift it instead of re-running".

Move

Add a lift rule mirroring the one it already has for the Slice Contract: when the brief carries a design-gate report path, its findings become the brief constraints and Phase 0 runs no lenses. design-gate's output contract already has the right shape for this.

saves up to 3 lens passes per slice
03

Ship names alternatives its workers cannot invokecontract

Station dispatch rule 2: a skill carrying disable-model-invocation: true "never appears in a worker's skill list… In this pipeline that is resolve-pr-feedback". But the phase-4 row also offers collaborative-delivery as an alternative build engine, and it carries the same flag. So do diverse-plan and review-gate, both of which the docs position as pipeline-adjacent.

A worker asked to use collaborative-delivery will find nothing by that name.

Move

Either drop the flag on collaborative-delivery (it is a build engine, not a top-level entry) or extend rule 2 to list every flagged skill a station may name, with the read-the-file-and-follow-it instruction. A one-line test in shared/tests can assert that no skill named in a station row is flagged.

closes a silent no-op path
04

A lens nobody routes tocontract

event-driven-microservices is a full design lens (event-stream contracts, single-writer ownership, choreography vs orchestration) and distributed-systems-patterns cites it seven times. But design-gate's routing table has no row for it, and to-tasks lifts its gate flags from that table. Under the "one user-called skill per step" principle, a lens the gate cannot reach only runs when you remember it exists.

Move

Add a routing row: "event streams, Kafka-style topics, choreography vs orchestration, event schema design → event-driven-microservices, data-systems-coding-lens". Or fold it into distributed-systems-patterns as a section, since the two already lean on each other.

makes the lens reachable by contract
05

Six runner skills are four-file shimsshape

kimi, glm, qwen, gemma each say "execute through the shared pi-runner implementation" with one provider/model pair pinned. muse and minimax do the same over cline-runner. Each shim is a SKILL.md, a script, and tests: roughly 500 words of prose that restate the parent.

The seat names still matter: discover_runners.py, the roster, and every panel routing file address seats by these names.

Move

Keep the seats, drop the skills. pi-runner --seat kimi and cline-runner --seat muse read the pin from model-roster.md; the probe keeps the seat vocabulary as aliases. Six directories become two tables.

68 → 62 skills, no seat lost
06

Four copies of the same panelshape

brainstorm, to-prd, to-tasks, and collaborative-delivery each ship an assets/*routing.toml declaring the same four providers (Opus synthesis anchor, Codex adversarial anchor, Gemini broad context, Kimi feasibility) with the same runner args and the same comment block about isolating cline state. Only the roles-per-phase differ. The restructuring notes already flagged stale model ids in "four routing files" once.

Move

One shared/assets/panel-providers.toml for the provider table; each skill keeps a 20-line file with only its phases and role assignments. panel_round.py merges the two. The roster stays the single source of model ids.

one place to rotate a seat
07

The council's tail is three skills that can only run after itshape

decide-about-disagreements and consensus-summary-html both begin by reading a finished models-consensus result and have no other input. Both are entry points, so the council cannot suggest them programmatically. diverse-plan is a fourth multi-model skill that explicitly "never calls the council" yet duplicates its seat probe, quorum rule, and degrade path.

Move

Make resolve and render two output modes of models-consensus (--then resolve, --html) that load the existing reference files; keep the old names as aliases for a release. Leave diverse-plan separate but have it import the council's preflight section instead of restating it.

62 → 60 skills, council reports self-describe their next step
08

Pairs that trigger on the same sentenceshape

  • advanced-react / react-performance: both "Advanced React (Makarevich)", both list re-renders, memo traps, stale closures, portals, fetch races. One says plan-and-implement, the other says advise-and-review. Only the latter is routed by design-gate.
  • explain-architecture / html-explainer: same question ("how does X work"), one answers in prose, one in a drill-down page.
  • summarize / session-handoff: already layered by design, but the layering is one --store flag wide.
Move

Merge each pair into one skill with a mode. React: react-performance with mode: plan | review. Explain: explain-architecture with format: prose | html, keeping the SVG-map reference. Leave summarize alone; its 34 lines are cheap and other skills borrow it by name.

60 → 58 skills, two trigger collisions gone
09

Two review orchestrators, one verify skill nobody else usesshape

full-review (28 files, ~20k words) and review-gate (15 files, ~5k words) both partition a diff, fan out reviewer personas across runner seats, and run an adversarial verification pass. review-gate alone calls verify-changes, the skill that discovers a repo's build/lint/test surface. Meanwhile ship phase 5 "runs the acceptance contract" by hand and implement-and-review preflight "detects how this project tests" by hand.

Move

Two steps. First, route both ship phase 5 and implement-and-review preflight through verify-changes; it already emits the machine-readable checks[] they want. Second, make the coverage contract and result JSON a gate mode of full-review, so one orchestrator serves both the human and the machine.

58 → 57, and one verification vocabulary
10

Three nested orchestrators, three ledgers per slicecost

ship keeps a run state per slice. implement-feature keeps a feature-level run state "beside the per-task states each implement-and-review keeps". implement-and-review keeps its own under .ai-workflow/impl-review/<id>/, with its own attempts, side-effect keys, and status flips. Each follows the same run-state-contract.md, so the shapes agree, but a resumed run has to reconcile three files that describe one slice.

The worktree flow is similar: worktree is a skill, yet implement-and-review mentions "worktree" 58 times and keeps "its internal flow" per the trigger audit.

Move

One ledger per slice, owned by the innermost engine, with the conductors holding only an index of slice → ledger path. That is already the "hand off the path, not the payload" rule applied to state. Then let implement-and-review invoke worktree for isolation instead of carrying a second copy of the git recipe.

one resume protocol, one recipe for git isolation
11

The biggest skills load their mechanics up frontcost

SKILL.md line counts: full-review 453, fable-mindset 393, browser-smoke 246, capture-learning 220, decide-about-disagreements 219, dynamic-harness 215. skill-expert, in this same repo, teaches progressive disclosure: a short SKILL.md that states the contract and loads references on demand. fable-mindset is meant to govern posture at the start of a turn, and it is the second-longest file in the collection.

Move

Cap SKILL.md at roughly 150 lines: triggers, inputs, workflow, output contract, gotchas. Move phase mechanics, personas, and rubrics into references/ the workflow names at the step that needs them. full-review already has the folder; it is a matter of moving text.

less context per invocation, same behavior
12

Orphans: skills with no path in and none outshape

html-explainer names no other skill and is named by none. knowledge-graph, cmux-cli, agents-md-craft, dcode-runner, opencode-runner, and advanced-react are each reachable only if you remember them. That is fine for utilities, but the README presents the collection as one workflow, and the orphans are where new users get lost.

Move

Add a "standalone utilities" list to the README and mark those skills disable-model-invocation: true consistently, so entry-point status means one thing. Where a link is natural, wire it: capture-learning can offer knowledge-graph once docs/solutions/ passes a size, and explain-architecture can offer the HTML format.

every skill is either on the map or labeled off it
