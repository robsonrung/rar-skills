00

brainstorm

Should we build this at all?

Digs into the motivation before the mechanism, explores the codebase, and widens the option set before narrowing it. Optional — skip it when the request is already concrete. If a design question can only be settled by running code, it detours through /prototype, which builds a throwaway and then throws it away.

hands off a verdict — BUILD / DEFER / REDUCE SCOPE / REJECT

With confidence and recommended scope. On BUILD it names the next step by hand.

01

interview-me

What exactly are we building?

Reads the glossary, the ADRs, and the code before asking you anything — a question that exploration could answer is not a question for you. That reading is delegated to a read-only worker that returns 01-grounding.report.md, so the conductor spends its context on the conversation and not on the repository. Then grills the angles that change what gets built: actors and permissions, edge cases, what's explicitly out of scope, data lifecycle, migration and rollback. It runs the security checklist while you're still here, and names the observable behaviour at the highest seam for each requirement.

hands off a decision record, in the conversation

Decisions, explicit assumptions with defaults, descoped items, security answers, named test seams. The exit test: every question the autonomous half would hit is answered, assumed, or descoped.

02

to-prd

Write it down

Does not interview you again — it synthesizes what station 01 already produced. This is the autonomy contract: the last artifact written while a human is in the room, so anything it omits becomes a question nobody downstream is allowed to ask.

hands off a PRD file under .ai-workflow/work/, status ready-for-agent

Two sections carry weight downstream: Security Decisions pre-marks which surfaces are sensitive, and Testing Decisions names the seams that become acceptance behaviours.

03

to-tasks

Cut it into slices you can approve

Breaks the PRD into tracer-bullet vertical slices — each one thin, complete through every layer, and demoable alone. Every slice gets a stable ID that is never renumbered, so later reorders and splits can't break a "blocked by" reference.

Each slice carries a Slice Contract: acceptance — exact commands verified to exist in your repo, plus behaviours lifted from the PRD's seams — and gates — which design lenses apply, and whether the deep security pass is required, read off the routing tables rather than re-decided.

Approval gate

You approve the breakdown once, in a five-question quiz. This is the last time anything asks you a question. Past this line, contested decisions go to a multi-model council instead of to you.

Autonomous · per slice, in a worktreeDesign gate, build, verify, deliver. Escalates rather than interrupts. Each station runs in its own subagent and hands the next one a report file — the conductor only ever sees a short envelope.
04

coding-design-plan → design-gate

Is the approach sound, before code exists?

The plan gets shaped and its test scenarios named; then the gate reads the slice's gates flags, picks at most three lenses from a lookup table, and runs them as parallel read-only reviewers. Choosing which architecture lens applies used to be a judgment call — that was itself a mid-flight question waiting to happen, so it became a table.

hands off 03-design-gate.report.md — one merged verdict, proceed | revise

A revise only blocks when it carries a concrete, load-bearing finding; cosmetic notes are listed and ignored. Lenses that disagree about a real trade-off escalate — they don't ask you.

05

implement-and-review

Build it, test-first

Lifts the contract rather than re-deriving it: the acceptance commands are the definition of done, the behaviours are the test-first targets, the gates flags select each track's lenses and the security pass, the expected review focus steers every reviewer, and the rollback note is a boundary the build must not cross. Frontend and backend build in parallel isolated worktrees where the implementer never reviews its own track, with /tdd running the red-green-refactor loop inside each.

Untested legacy code gets a characterization net from /safe-incremental-coding first. Bugs found mid-loop go to /diagnose, never to a guess.

hands off 04-implement.report.md — merged code + verification evidence

Which tests were inspected, which were added, which ran, and what they proved. A behaviour change that arrives without coherent evidence gets exactly one recovery attempt, then hard-blocks.

06

Verify — ordered, fail-fast

Cheapest check first; the expensive gate reads final code

01acceptanceRun the slice's own commands.
02coding-review-simplifySelf-simplify while context is fresh. Mutating.
03full-reviewSpecialists, multi-model triangulation, execution-verified bugs.
04browser-smokeDrive the real pages the diff touched.

The order is load-bearing and was previously wrong: the expensive multi-model gate used to run before a mutating simplify pass, so the reviewed code and the shipped code weren't the same code. Failures loop back to station 05 through /diagnose.

hands off 05-verify.report.md — green slice + residual findings, made durable

Review findings that were not applied get filed rather than dropped — a finding nobody acted on still has to survive the run.

07

open-pr → resolve-pr-feedback

Ship it

The PR body carries acceptance evidence, the design-gate verdicts, the review summary, and a decision log naming every assumption taken on your behalf. When review comments land, each one is judged against the actual code — valid ones fixed, invalid ones answered with evidence — then the threads are resolved.

Your only remaining job is merging.

How the conductor stays thin

hand off the path, not the payload

A relay only works if the runner isn't carrying every previous leg. Each autonomous station runs in its own subagent; three artifacts move between them, and only the smallest one re-enters the conductor.

in<NN>-<station>.brief.mdTen fields, one screen. Inputs are paths — a brief that quotes the last report's body has already lost the point.
out<NN>-<station>.report.mdSeven fixed sections: verdict, what ran, evidence, decisions, findings not applied, inputs for the next step, artifacts. Fixed so the next brief can cite a heading.
backthe envelopeUnder 15 lines of JSON — status, verdict, the report's path. The only thing that enters the conductor's context.

So the conductor holds the run-state path, the slice id, and one envelope per finished station. It opens a report body only to route a revise, to assemble the final report, or to reconcile two stations that disagree. Everything else it can name without having read. The same discipline is what makes a compaction survivable: the reasoning was written to disk instead of spoken into the transcript.

Two constraints shape where the line falls. Stations 00–03 stay in the conductor's own context because only it can ask you — though station 01's reading of the glossary, the ADRs, and the code is delegated anyway, since that part was never conversation. And a station's own fan-out — the design lenses, the review seats — reaches its models through the runner CLIs rather than nested subagents, which is what discover_runners.py probe --native-agent no is for.

File ordinals follow ship's phase numbers, which merge stations 01 and 02 into one Specify phase — so station 04 on this sheet writes 03-design-gate.report.md. Contracts: shared/references/handoff-contract.md for the shapes, ship/references/station-dispatch.md for the per-station binding.

What replaces asking you

after the gate

The autonomous half is only honest if it has somewhere to go when it's genuinely unsure. Three rungs, in order.

  1. Ask the other models. models-consensus in poll mode: a blind fan-out to every available seat, five-dimension reconciliation, one gap-repair round, two judges, then a dedicated synthesizer. Read-only, and it never starts implementing.
  2. Take the most reversible default and record the assumption in the decision log that reaches the PR body.
  3. Stop for a human — only for something destructive or irreversible: data deletion, force-push, external publication, a migration against real data.

What changed

68 → 56 skills

Two problems. The pipeline referenced four skills that didn't exist in the repo — including the interview and the test loop, its first and fourth working steps. And several skills competed at the same step, each one a fork in the road an agent had to resolve mid-flight.

Five skills were added, each filling a step the pipeline already called for: interview, tdd, diagnose, prototype, and fable-mindset. The pipeline now runs entirely on skills that exist in this collection.
