# Audit and Validation

Use for an instruction audit or substantial restructure. For a small edit, select only the affected checks. This is a coverage guide, not a mandatory second review pass.

## Inspect the instruction set

1. Scope: an audit reports; a create or update request writes its authorized files.
2. Grounding: purpose, commands, layout, constraints, and team rules have repository or user evidence.
3. Placement: the root carries broadly useful rules; conditional guidance has a clear loading trigger.
4. Preservation: security boundaries, team standards, and required checks remain available to the consumer that needs them.
5. Context: no routine edit requires a full repository read or a stack of unrelated documents.
6. Verification: commands come from actual definitions. A command list is not an instruction to execute every entry.
7. Authority: existing permission is reused; unresolved external effects and material decisions retain their approval boundary.
8. Coherence: dual instruction files follow the host and project conventions without conflicting copies.
9. References: changed paths, symbols, and line pointers resolve. Do not create empty supporting files.

## Validate the changed contract

Use repository guards when available. Check links mechanically and inspect command definitions. Run a command to verify an unresolved claim only when its action is authorized. An instruction-file edit alone does not authorize deployments, migrations, external messages, or destructive operations.

Reuse earlier evidence when the relevant content and assumptions still match. Do not add tests that assert rewritten prose or create example bundles for routine edits.

When the user requests behavior evaluation, select bounded cases through `skill-expert`: a small local edit, a subsystem-specific task, or a real authority boundary can expose different loading and permission behavior. Keep measured results separate from static inspection.

## Report

Name the canonical file and any supporting files changed, the reason for the change, preserved constraints, validation evidence, and unresolved facts. Counts can show text reduction; they do not prove faster or more reliable execution.

An audit includes the instruction and location, why it matters, and the proposed change. An authorized edit does not need a second approval to apply that change.
