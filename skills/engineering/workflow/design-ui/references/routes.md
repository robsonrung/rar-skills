# Workflow selection

## Existing product

Inspect the target route, neighboring screens, shared components, tokens, and actual behavior. Form a concrete design hypothesis, such as keeping actions beside selected rows and preserving filter context during editing.

Retain useful navigation, density, terminology, primitives, and visual identity unless changing them is in scope. Verify precedents in actual files. Do not infer that a component exists from a guessed filename.

For small changes, implement one improvement and inspect it. For a meaningful layout choice, compare alternatives through `to-prototype`, using the established system. Decorative heroes or dramatic backgrounds rarely resolve an operational workflow problem.

## Image concepts

Use when visual identity or composition is unresolved, or the user requests images before code.

1. Specify identical product, audience, task, copy, sample data, viewport, and state across candidates.
2. Vary composition, hierarchy, density, typography, imagery, or navigation deliberately.
3. Generate separate actual images with the available image tool. Follow its rules for supplied references and transparency.
4. Present comparable sizes and aspect ratios. Preserve full size versions for detail inspection; contact sheets can conceal defects.
5. Label outputs as concepts. Pictured controls are not functional and generated text is not automatically approved copy.
6. Compare against the brief. If approval is required, show the real options and a recommendation, then wait for that decision.
7. Extract the selected design contract before implementing. Design responsive behavior and hidden states separately.

If image generation is unavailable and images are explicitly required, prepare the brief and generation prompts, state the blocker, and preserve the checkpoint. Do not silently build HTML and call it image generation. If the medium is flexible, use executable concepts and briefly explain why.

Do not create a new target merely because implementation misses the selected one. Preserve the approved direction and disclose material adaptations.

## Executable alternatives

Use when deciding between inline editing and a drawer, a page and a wizard, table and split view, navigation patterns, gestures, or animation. Build them through `to-prototype`, which owns the scratch location, fixtures, and disposal.

Hold content, task, viewport, and design system constant. Give each version the interaction and recovery behavior the comparison needs, run the same scenario in each, and compare clarity, steps, context retention, recovery, keyboard use, and mobile behavior. One flow usually resolves the uncertainty; do not build several complete applications. The representative slice rebuilds the winner.

## Selected reference

Read available design context, tokens, component metadata, and assets. Preserve the chosen visual target and content.

For screenshots, infer layout and hierarchy but label behavioral assumptions. For structured design files, use semantic component and token information. When source code exists, evolve it instead of rebuilding from pixels alone.

Use native layout, real text, semantic controls, and suitable chart components. Keep standalone illustrations separate from the interface. Compare the actual browser result with the reference at matching size and state.

## Combined work

Use images for visual direction, an executable slice for consequential interaction, and existing components for coherence. Change routes only to answer an unresolved question.

A faithful implementation of an unusable image needs a documented adjustment. An attractive redesign also fails when the request was faithful implementation of an approved reference.

## Honest fallbacks

Respect explicit tool denials. Do not use alternate surfaces, flags, or indirect execution to bypass a blocked verification action. When no permitted route remains, complete useful independent work and mark the affected gate unverified.

1. No browser access, complete useful implementation or planning and state that rendered and behavioral verification remains outstanding.
2. No independent reviewer, perform a separate critical pass labeled self review, and report independent review as not performed. Report the reviewer's actual model; never claim provider diversity it lacks.
3. No brand system, infer a compact task specific system and record assumptions.
4. No backend, use clearly identified fixture behavior when a prototype is authorized.
5. No publishing permission, finish and verify the authorized local deliverable.

Spend effort on the largest uncertainty. Favor hierarchy before decoration and one complete realistic task before many polished static screens.
