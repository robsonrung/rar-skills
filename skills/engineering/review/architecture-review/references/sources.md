# Sources and attribution policy

The original bibliography is retained and translated. Public terminology references added or rechecked for this update are identified by their access notes. The check date is September 26, 2026. A publisher page, table of contents, or chapter excerpt is not a claim to have read the entire book. This is a complementary reading list, not an objective ranking of the best books.

For each important finding, connect the relevant concept to an actual system observation. Literature establishes an analytical lens; it does not prove that the repository has a defect. Use `sources` only for references actually applied in that report. Do not append the entire catalog by default.

The terminology baseline for Designing Data-Intensive Applications is the first edition. Later editions and database implementations may use different wording or guarantees. Verify current library support, engine semantics, platform limits, security advisories, and prices in official versioned documentation during the audit. Record uncertainty when verification is unavailable.

Descriptions in this package are concise paraphrases and practical assessment questions, not reproductions of the books. DDD Reference material is attributed to Eric Evans and its CC BY 4.0 notice. The Leitwörter authoring convention was supplied with the revision request; its application here is an authoring method, not a demonstrated improvement in model reliability.

## Disagreements require judgment

Clean Code and A Philosophy of Software Design do not prescribe the same decomposition choices. Compare actual comprehension and change costs. DDD Tactical Building Blocks are not mandatory for a simple CRUD application. Microservices are not an inevitable maturity stage. Unit Tests and Integration Tests protect different risks. Events do not automatically remove coupling.

Treat the harness engineering article as a practice report from one context. Its particular layering, merge policy, and operating choices are not requirements here. The audited system's quality and safety constraints take precedence.

Do not invent chapter quotations, page numbers, benchmarks, or improvement percentages. Explain where a recommendation is your synthesis. Prefer a source's precise guarantee over an attractive but stronger paraphrase.
