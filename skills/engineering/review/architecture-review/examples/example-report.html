1. Verdict

The modular monolith is fit for purpose for the declared workload of a few hundred orders per day. One risk needs action now: payment capture and order state commit in separate transactions, so a timeout after capture can leave a paid order marked unpaid. The first move is a small outbox for the capture call, not a new service.

5. Findings

One root cause: the payment effect and the order state have no shared commit.

P1 Payment capture and order commit are not atomic

A timeout after capture leaves a paid order unpaid. Record capture intent in the order transaction and deliver it from an outbox. No lost payments; retry-safe.

End-to-end correctness fails across the capture timeout window, because the capture call and the order commit run in separate transactions (E001).

Details
Observation
checkout() captures, then opens a new transaction to mark the order paid.
Impact
A provider timeout after capture charges the customer without a paid order (Q1).
Recommendation
Write a capture intent row with the order and deliver it with an idempotency key; this restores end-to-end correctness at the cost of one table and one worker.
Alternatives
Keep as is and reconcile by hand from provider reports; acceptable only below a few incidents per month.
When not to act
The provider guarantees synchronous capture results with no timeout path.
Acceptance
A test that times out the provider after capture ends with exactly one paid order and one capture.
Rollback
Disable the worker and drain the outbox by hand; captured payments need reconciliation, not rollback.
