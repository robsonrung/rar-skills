Risks and improvements

Each finding connects an observation, its effect and a verifiable action.

Visible findings: 5

F001 · D09P1True externalConfidence: High

A committed order can appear to fail

Problem: A committed order can be reported as failed.

Change: Persist intent and deliver through an outbox with explicit confirmation.

  • no duplicate orders on retry
  • recovery is observable

Decision anchor: end-to-end correctness

End-to-end correctness is not protected by the local commit alone, E002. Clarify confirmation semantics before selecting a recovery mechanism.

In the fictional flow, the order write commits before the ERP call. An external timeout becomes an error response even though the order already exists.

The user may retry without knowing the order was committed. The risk is a duplicate business effect, not just a poor error message.

Linked incident: FICTIONAL EXAMPLE: a support ticket describing a duplicate order after a timeout.

E002E003E006
Solution, alternatives and verification

Smallest useful change

Protect end-to-end correctness by defining confirmation semantics. If deferred integration is allowed, persist the order and publication intent in one local transaction, then deliver with an explicit idempotency and recovery contract.

Cost and trade-off

Adds pending state, recovery processing, and queue visibility. It does not by itself require a broker or microservices.

Effort and estimate basis

Medium, relative: touches the write path, response contract, and recovery. No calendar estimate is available.

Why act now

The ambiguity affects the main business flow and order integrity in the example.

When not to change

Do not introduce asynchronous confirmation when ERP approval is required for order validity; redesign the confirmation protocol instead.

How to verify

Proposed isolated Integration Test: ERP timeout, duplicate input, and resumed delivery. Assert end-to-end correctness using final local and external state. Not run.

Acceptance criterion

Under the agreed effect boundary: one business effect per command, explicit integration state, and observable recovery. This is a proposed criterion, not an achieved guarantee.

Rollback

Keep schema and read-path compatibility. Drain or reconcile pending intents before disabling the worker; do not delete already-used outbox records.

Alternatives

  • Keep synchronous integration with explicit state and recovery semantics when external confirmation is mandatory.
  • Use an existing transactional job mechanism if it provides the required guarantees.

Glossary

Bounded Context
The explicit boundary within which a particular domain model and its language are consistent.
The Dependency Rule
Source code dependencies point toward higher-level policy, not outward toward implementation details.
Entities
The Clean Architecture policy layer containing the most general enterprise business rules.
Use Cases (Interactors)
Application-specific business rules that orchestrate Entities and the steps needed to achieve an application goal.
Interface Adapters
Code that converts representations between policy and external delivery or persistence mechanisms.
Component Coupling
Principles governing dependencies among components and their stability.
Transactional Outbox
Persist business state and a publication intent in the same local transaction, then deliver that intent separately.
Effectively-Once Processing
A common community term for making repeated processing attempts produce one observable effect within an explicitly defined boundary.
seam
A point where behavior can be changed without editing the code at that point; an enabling point controls which behavior is used.
behavior-preserving
Refactoring changes internal structure while preserving the behavior included in the agreed contract.
deterministic oracle
A verification rule whose verdict is reproducible under controlled inputs, state, and explicitly stated assumptions.
Idempotency
Repeating the same identified operation has the same intended effect as applying it once, within the declared contract and retention scope.
p95
The percentile below which approximately 95 percent of observations fall for the stated sample and conditions.
SLO
A measurable service-level objective agreed for a defined scope and time window.
